# Build Evaluation — Stream UI (2026-02-01)

## Project
Live stream viewer control bar for camservice (Raspberry Pi camera).

## Three Approaches Compared

### Approach 1: Single Sub-Agent, All Tasks
- **Method:** Spawned one sub-agent with full spec, told it to do all 6 tasks
- **Result:** ❌ Failed quality inspection
- **Time:** ~3 min
- **Why it failed:** Sub-agent accumulated context across 6 changes. No verification between tasks. Errors compounded. Output looked "done" but wasn't right.
- **Equivalent to:** Asking someone to build an entire feature without checking in

### Approach 2: Orchestrated, One Task Per Sub-Agent (Feature Build)
- **Method:** TASKBOARD.md with dependency graph. Orchestrator spawns one builder per task, verifies each commit, then spawns next.
- **Result:** ✅ All features implemented, 13/13 automated checks passed
- **Time:** ~4 min (5 builders × 20-55s each + verification gaps)
- **Tasks:** 5 builder tasks + 1 orchestrator QA
- **Why it worked:** Each builder had fresh context, ONE job, exact code to write, and validation commands. Orchestrator caught issues between tasks.

### Approach 3: Orchestrated, One Task Per Sub-Agent (Bug Fixes)
- **Method:** Same TASKBOARD approach, focused on 3 specific bugs
- **Result:** ✅ All fixes applied, 9/9 checks passed
- **Time:** ~2 min (3 builders × 20-25s each)
- **Why it worked:** Same method, even tighter scope per task

## Key Insights

### 1. Smaller scope = higher quality
Each builder doing ONE thing produced cleaner output than one builder doing SIX things. The token cost per builder was actually LOWER because less context to process.

### 2. Orchestrator verification is essential
The orchestrator (main session) checking `git log`, running validation commands, and confirming results before spawning the next task is what prevents error compounding.

### 3. Exact code in the task brief > vague instructions
When the task brief included the EXACT code to write (not just "fix the time display"), builders executed precisely. Vague briefs led to interpretation drift.

### 4. Dependency ordering matters
Task 2 (time display JS) depended on Task 1 (server endpoint). Building them in order meant Task 2's builder could trust the endpoint existed. Parallel execution would have caused issues.

### 5. TASKBOARD as shared state
The TASKBOARD.md file gave the orchestrator a clear checklist and gave each builder context about where their task fit. It's the coordination mechanism.

## What To Improve Next Time

### A. Visual verification gap
We had automated checks (ast.parse, curl endpoints, feature grep) but NO visual verification between tasks. The quality issues in Approach 1 were visual (scrubber bouncing, sync problems) — things only visible by looking at the actual UI. 

**Proposal:** After each builder commits, orchestrator should start the stream and take a screenshot or ask the human to verify before proceeding.

### B. Task briefs could be even more surgical
Some builders had to "find" code and figure out where to insert. Better: give line numbers or exact surrounding context for insertions.

### C. Evaluation should happen DURING the build, not after
This eval is retrospective. Next time, log metrics as each builder completes so the orchestrator can adapt in real-time.

### D. Separate concerns more aggressively
The original "final polish" spec mixed server changes (Python) with UI changes (JS/CSS). These should have been separate taskboards with separate validation criteria.

## The Method (Portal1 Build Method v2)

```
DISCUSS → SPEC → TASKBOARD → [SPAWN → VERIFY]×N → QA → TAG
```

1. **DISCUSS** — Talk through what we're building
2. **SPEC** — Write *_SPEC.md with design + behaviors
3. **TASKBOARD** — Dependency graph, one row per task, validation commands
4. **SPAWN** — One sub-agent per task, exact code in brief
5. **VERIFY** — Orchestrator checks commit, runs validation, confirms
6. **QA** — Orchestrator does final review (ideally with visual check)
7. **TAG** — Git tag the working checkpoint

Each SPAWN→VERIFY is one iteration. Fresh context. One concern. Validated before next.

## Comparison to Ralph Loops

| Aspect | Ralph Loops | Portal1 Build Method |
|--------|------------|---------------------|
| Context management | Fresh CLI session per iteration | Fresh sub-agent per task |
| Task tracking | IMPLEMENTATION_PLAN.md | TASKBOARD.md |
| Orchestration | Loop script (automated) | Main session (conversational) |
| Backpressure | Tests, lint, type-check | ast.parse, curl, feature grep |
| Human involvement | Reviews plan, sets specs | Reviews output, gives feedback between passes |
| Scope per iteration | One task from plan | One task from taskboard |
| Commit discipline | Per iteration | Per task |

**Key difference:** Ralph is fully autonomous (loop script runs unattended). Our method is orchestrator-guided — the main session decides what to build next based on human feedback. This is better for our use case because we're doing UI work that needs visual evaluation.
