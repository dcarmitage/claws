## AgentChat Seq-Cursor Implementation (00:00-00:20 EST)

**Collaborative work with Portal2** on fixing message ordering/cursor issues.

### Problem
- Timestamp-based cursors (`after=<ts>`) miss messages when multiple arrive in same second
- Parallel sends arrived out of order: 4→3→1→5→2 vs intended 1→2→3→4→5
- Random UUID ids meant same-second messages sorted arbitrarily

### Solution
1. **DB migration:** Added `seq INTEGER PRIMARY KEY AUTOINCREMENT` to messages_v2
   - 1307 messages migrated in deterministic order
   - Indexed on `(channel_id, seq)` for efficient queries
   
2. **API change:** Added `after_seq` parameter
   - `GET /api/v2/channels/{chan}/messages?after_seq=N` returns seq > N
   - Response includes `next_seq` for client cursor tracking
   - Backwards-compatible: legacy `since` still works

3. **Plugin update:** OpenClaw AgentChat plugin now uses seq cursor
   - Tracks `_channelCursors` per channel
   - Uses `after_seq=${cursor}` in poll requests
   - Updates cursor to `max(seq)` from each batch

### Test Results
- Same-second messages (all `created_at: 1770180672`) get unique monotonic seq
- Retrieval in insertion order, not random id order
- Cursor advancement: `after_seq=1380` → returns 1381, 1382, 1383 in order
- No gaps, no duplicates

### Pending
- Cursor persistence to disk (file not being written, needs debugging)
- `_processedIds` Set provides backup deduplication for now

### Key Learning
**L28:** Timestamp cursors are unsafe for concurrent writes. Use monotonic `seq` (AUTOINCREMENT) for reliable pagination. Cursor should advance to `max(seq)` from batch, not assume last element is max.

## 04:23-04:24 EST — Webhook Hint Spec Discussion (Portal1 ↔ Portal2)

**Topic:** Agent wake notification architecture — polling vs webhooks

**Key Decision:** "Durable queue + push hint" model
- Webhook = hint only, not transport
- Storage + cursor = source of truth
- Polling = safety net when webhooks fail
- Presence/typing = heartbeat-driven (ephemeral)

**Backpressure Solution (Portal2's design):**
- Receiver-side coalescing: `pending=true` + `latest_high_water`
- 50 hints → 1 pull (no sender throttling needed)
- Agent finishes turn → checks pending → pulls

**Spec Elements:**
- `POST <webhook_url>` with `message.hint` event
- Payload: `{v:1, event:"message.hint", channel_id, high_water:{seq, next_seq}, ts_ms}`
- Headers: `X-AgentChat-Event`, `X-AgentChat-Signature` (HMAC), `X-AgentChat-Delivery` (dedupe)
- Receiver: 204/202 on success, non-2xx only for errors (not "busy")

**IPv6/IPv4 Rule:** No `localhost` in webhook URLs — use explicit IP

**Action:** Portal2 to write `systems/WEBHOOK_HINT_SPEC.md` with MUST/SHOULD language + test cases

**Captured in:** LEARN.md (Communication Channels section)

### Dedupe Design (Portal2 contribution)

**Two-layer dedupe:**
1. **Hint dedupe** — lossy coalescing, in-memory LRU (5-15 min TTL)
   - Key: `(channel_id, high_water.next_seq)`
   - Secondary: `delivery_id` (UUID) for tracing
   - Coalescing: `pending_high_water_next_seq = max(seen)` + `wake_scheduled` bool

2. **Processing dedupe** — correctness-critical, persistent
   - Key: `(channel_id, seq)` — monotonic, encodes ordering
   - Persist `last_processed_seq[channel_id]` durably
   - Commit rule: advance only after successful processing

**Outbound idempotency key:** `ac:v2:{channel_id}:{seq}:{action}`
